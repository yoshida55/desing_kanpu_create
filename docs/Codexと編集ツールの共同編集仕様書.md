# Codex と編集ツールの共同編集仕様書

> **最初に全体の流れを確認する：**
> [図で見る「Codexと編集ツールの共同編集」概要](./Codexと編集ツールの共同編集_概要.html)
>
> HTML は人が流れをつかむための概要資料です。実装条件・例外・テストの正本は、この Markdown 仕様書です。

## 1. この仕様の目的

この仕様は、同じキャンプ HTML を次の順序で安全に編集できるようにするためのものです。

1. ユーザーが既存のデザイン編集ツールで、要素を移動・拡大縮小・文字変更など自由に編集する
2. Codex が、位置ずれや余白、文字組み、画像、色などを整える
3. ユーザーが再び既存のデザイン編集ツールで開き、通常どおり編集を続ける
4. 上記を何度繰り返しても、編集ツールの選択・移動・保存機能が壊れない

この仕組みの狙いは、Codex に既存 HTML の `div` 構造を直接書き換えさせることではない。

Codex の変更を、編集ツールが理解できる「変更データ」として渡し、編集ツール側で安全に HTML へ取り込むことが目的である。

---

## 2. 結論と保証範囲

### 2.1 想定する運用

以下の運用であれば、ツール → Codex → ツールの往復編集を成立させられる。

```text
編集ツールで編集・保存
        ↓
Codex は HTML を直接変更せず、パッチファイルを作成
        ↓
編集ツールでページを開くと、パッチが先に適用される
        ↓
ユーザーが編集ツールで確認・追加編集・保存
        ↓
パッチの結果が正式な HTML に取り込まれ、パッチは消化済みになる
```

### 2.2 保証できる条件

次の条件をすべて守ること。

- Codex はキャンプ HTML を原則として直接編集しない
- Codex は本仕様のパッチ API または専用 CLI だけで変更を作成する
- 各編集対象には、保存後も変わらない安定 ID を付ける
- パッチは編集バーの初期化より前に適用する
- ツールで保存するとき、適用済みパッチを HTML に正式反映する
- 保存時に、HTML とパッチの世代が一致しているか検証する
- 対応していない構造変更は Codex に実行させない

### 2.3 保証できない操作

初期版では、次の操作を安全とはみなさない。

- Codex が HTML ファイルを直接開いて `div` を追加・削除する
- Codex が要素の親子関係や並び順を自由に変更する
- Codex が編集ツール用の `data-ce*` 属性を独自判断で削除・変更する
- Codex が編集ツールの JavaScript や保存処理を、その都度書き換える
- HTML とパッチを同時に別プロセスから保存し、競合検知を行わない

これらを許すと、画面上は正しく見えても、次にツールで選択・移動・保存した時点で壊れる可能性がある。

## 3. 基本設計

### 3.1 正式データと作業データ

役割を次のように分離する。

| データ | 役割 | 主な更新者 |
|---|---|---|
| キャンプ HTML | 現在の正式なページ | 編集ツールの保存処理 |
| Codex パッチ | HTML に対する未確定の変更 | Codex 専用 API / CLI |
| 画像などのアセット | ページから参照する素材 | ツールまたは専用アセット処理 |
| 適用レポート | 適用成功・対象不明・拒否操作の記録 | サーバー |

重要事項：Codex の変更中も、キャンプ HTML 自体を作業ファイルとして扱わない。

### 3.2 パッチの保存場所

推奨例：

```text
data/
  camp/
    example.html
  camp_patches/
    example.patch.json
  camp_patch_history/
    example/
      000001.applied.json
```

実際のディレクトリ名は既存設定に合わせてよいが、HTML とパッチは別ファイルにする。

### 3.3 安定 ID

Codex が変更対象を正確に識別するため、編集可能な要素に永続的な ID を付ける。

```html
<div data-ceid="ce_01k2abc...">...</div>
```

`data-ceid` は要素を特定するためだけに使用する。

現在使われている `data-cetx`、`data-cety`、`data-cesx`、`data-cesy`、`data-cero`、`data-cebt` などは、位置や変形の状態であり、要素 ID の代わりにしてはならない。

安定 ID の要件：

- ページ内で一意である
- 通常保存では変わらない
- ランダム UUID、ULID、または同等の衝突しにくい値を使う
- 表示内容、クラス名、DOM の順番から ID を生成しない
- 要素を複製した場合は、複製先とその子要素に新しい ID を発行する
- お気に入りセクションなどを挿入する場合も、新しいページ用の ID に振り直す
- 要素削除後に同じ ID を再利用しない

### 3.4 `cleanSection()` との整合

現在のセクション整理処理では、多くの `data-ce*` 属性が削除対象になる。

実装時は次のどちらかに統一する。

推奨方式：

- 通常保存では `data-ceid` を維持する
- セクションをお気に入り素材として保存するときは、素材側の ID を削除する
- 素材をページへ挿入するときに、新しい ID を再発行する

単純にすべての場面で `data-ceid` を残すと、同じお気に入りセクションを複数回挿入した際に ID が重複する。そのため、保存と素材化を区別すること。

## 4. Codex パッチ形式

### 4.1 基本形式

```json
{
  "schemaVersion": 1,
  "targetFile": "example.html",
  "baseSha256": "HTML保存時点のSHA-256",
  "revision": 3,
  "createdBy": "codex",
  "createdAt": "2026-08-02T12:00:00+09:00",
  "updatedAt": "2026-08-02T12:10:00+09:00",
  "operations": [
    {
      "op": "set_style",
      "target": "ce_01k2abc...",
      "property": "left",
      "value": "1030px",
      "priority": "important"
    }
  ]
}
```

### 4.2 必須フィールド

| フィールド | 内容 |
|---|---|
| `schemaVersion` | パッチ仕様のバージョン。初期値は `1` |
| `targetFile` | 対象 HTML のファイル名。絶対パスは禁止 |
| `baseSha256` | Codex が変更を作った時点の正式 HTML の SHA-256 |
| `revision` | パッチを更新するたびに増える整数 |
| `createdBy` | `codex` など変更元を示す値 |
| `operations` | 適用する操作の配列 |

### 4.3 初期版で許可する操作

#### スタイル設定

```json
{
  "op": "set_style",
  "target": "ce_xxx",
  "property": "top",
  "value": "120px",
  "priority": "important"
}
```

#### スタイル削除

```json
{
  "op": "remove_style",
  "target": "ce_xxx",
  "property": "box-shadow"
}
```

#### 安全な属性設定

```json
{
  "op": "set_attribute",
  "target": "ce_xxx",
  "name": "alt",
  "value": "パソコン作業の様子"
}
```

#### 安全な属性削除

```json
{
  "op": "remove_attribute",
  "target": "ce_xxx",
  "name": "title"
}
```

#### 画像差し替え

```json
{
  "op": "replace_image",
  "target": "ce_xxx",
  "src": "/uploads/work-pc-v2.png",
  "alt": "パソコン作業の様子"
}
```

#### 文字変更

```json
{
  "op": "set_text",
  "target": "ce_xxx",
  "value": "自分のペースで、丁寧に取り組めます。"
}
```

`set_text` は、子要素を持たない文字専用要素に限定する。アニメーション用の `span` や装飾用の入れ子がある要素に `textContent` を直接設定すると、内部構造が失われるためである。

### 4.4 初期版で禁止する操作

- `innerHTML` の任意置換
- 任意 JavaScript の実行
- `insertAdjacentHTML`
- 要素の自由な追加・削除・移動
- イベント属性の追加（`onclick` など）
- `data-ceid` の変更・削除
- 編集ツール内部で使用する `data-ce*` 属性の直接変更
- `<script>`、`<iframe>`、`<object>` などの挿入

### 4.5 べき等性

同じパッチを誤って二度適用しても、結果が二重にならない操作だけを使う。

たとえば `left` を `1030px` に設定する操作は安全だが、「現在の left に 20px 加える」という操作は禁止する。

## 5. パッチ適用のタイミング

### 5.1 ページを開くとき

`/camp/<filename>` の処理を、概念上は次の順序にする。

```text
1. 正式 HTML を読み込む
2. 対応するパッチを読み込む
3. パッチの形式・対象ファイル・世代を検証する
4. DOM にパッチを適用する
5. 適用結果を記録する
6. 編集バーと編集機能を初期化する
7. ブラウザへ返す
```

パッチは編集機能の初期化より前に適用する。

これにより、編集ツールは Codex の変更後の DOM を通常のページとして認識し、そのまま選択・移動・保存できる。

### 5.2 適用方法

各操作は、次のセレクターで対象を探す。

```js
document.querySelector('[data-ceid="ce_xxx"]')
```

適用結果は次の三種類に分ける。

- `applied`: 正常に適用した
- `missing_targets`: 対象 ID が現在の HTML にない
- `rejected_operations`: 不正または禁止された操作

対象が見つからない操作が一つあっても、ページ全体を壊してはならない。該当操作を無視して警告を表示し、保存前にユーザーが把握できるようにする。

### 5.3 パッチ適用用の一時データ

パッチ適用のために一時的な `<script>` や管理用属性を注入する場合、それらは `cleanHtml()` の保存対象から除外する。

ただし、パッチが変更した通常の `style`、文字、画像 URL などの結果は保存対象に含める。

## 6. ツール保存時の取り込み処理

### 6.1 保存の意味

ユーザーが編集ツールで「変更を保存」を押した時点で、画面上に適用されている Codex パッチを正式 HTML に取り込む。

保存成功後は、同じパッチを次回読み込み時に再適用してはならない。

### 6.2 ブラウザから送る情報

既存の保存データに、最低限次を追加する。

```json
{
  "filename": "example.html",
  "html": "整理済みのHTML全文",
  "baseSha256": "ページを開いた時点のHTMLのSHA-256",
  "appliedPatchRevision": 3
}
```

### 6.3 サーバー側の保存手順

対象ファイル単位のロックを取得し、次の順序で処理する。

```text
1. filename が CAMP_DIR 内の .html であることを確認
2. 現在の正式 HTML の SHA-256 を計算
3. 受信した baseSha256 と比較
4. 現在のパッチ revision と appliedPatchRevision を比較
5. 不一致なら HTTP 409 を返し、何も上書きしない
6. 既存の finalize 処理を実行
7. 一時ファイルへ書き込む
8. os.replace 相当の原子的置換で HTML を確定
9. 適用済みパッチを履歴へ移動、または消化済みにする
10. 新しい HTML の SHA-256 を返す
```

重要事項：HTML の保存が成功する前にパッチを削除してはならない。

HTML 保存には成功したがパッチ整理に失敗した場合も、次回に二重適用されないよう、適用済み revision を別の状態ファイルへ記録するなど、トランザクション相当の扱いにする。

### 6.4 競合時の動作

以下の場合は保存せず、HTTP 409 を返す。

- ページを開いた後、別の画面から同じ HTML が保存された
- ページを開いた後、Codex がパッチを更新した
- Codex が古い HTML を基準にパッチを作成した

ユーザー向け表示例：

```text
このページは別の編集によって更新されています。
上書きすると変更が失われるため保存を中止しました。
ページを再読み込みし、変更内容を確認してください。
```

競合時に「最後に保存した方を正」として強制上書きしてはならない。

## 7. Codex 専用インターフェース

Codex に JSON を手書きさせるだけでは、入力ミスや禁止操作を防ぎにくい。そのため、検証付きの API または CLI を用意する。

### 7.1 推奨 CLI

```powershell
python tools/camp_patch.py inspect --file example.html
python tools/camp_patch.py set-style --file example.html --id ce_xxx --property left --value 1030px --important
python tools/camp_patch.py remove-style --file example.html --id ce_xxx --property box-shadow
python tools/camp_patch.py set-text --file example.html --id ce_xxx --value "新しい文章"
python tools/camp_patch.py replace-image --file example.html --id ce_xxx --src /uploads/work-pc-v2.png --alt "パソコン作業"
python tools/camp_patch.py validate --file example.html
python tools/camp_patch.py report --file example.html
```

`inspect` は Codex が対象を選べるよう、少なくとも次を返す。

- `data-ceid`
- タグ名
- class
- 省略した表示文字
- 位置・サイズ
- 現在の主要 style
- 親要素の `data-ceid`
- 画像の場合は `src` と `alt`

### 7.2 推奨 API

必要に応じて次を実装する。

| メソッド | パス | 用途 |
|---|---|---|
| `GET` | `/api/camp_patch?file=...` | 現在のパッチと対象情報を取得 |
| `POST` | `/api/camp_patch` | 検証後に操作を追加・更新 |
| `POST` | `/api/camp_patch/validate` | 適用可能性を検証 |
| `GET` | `/api/camp_patch/report?file=...` | 適用結果を取得 |

API を作る場合も、最終的なファイル検証・操作検証はサーバー側で行う。

### 7.3 Codex に与える作業ルール

Claude Code の実装後、Codex には次のルールを明示する。

```text
- camp HTML を直接編集しない
- viewer.py を案件ごとに変更しない
- camp_patch.py または camp_patch API を使う
- inspect で対象 ID を確認してから変更する
- validate が成功してから作業完了とする
- 構造変更が必要なら勝手に実行せず、未対応操作として報告する
```

## 8. 対応する編集内容

### 8.1 初期版で対応するもの

- 要素の `top`、`left`、`right`、`bottom`
- `width`、`height`、`max-width` などの寸法
- `margin`、`padding`、`gap`
- 文字サイズ、行間、文字間、色、太さ、整列
- 背景色、枠線、角丸、影、透明度
- 安全な transform 値
- 画像 URL、alt、object-fit、object-position
- 子要素を持たない文字要素の本文
- 安全な `aria-*` 属性

編集ツールが inline style に `!important` を使用しているため、パッチは `priority` を保持できるようにする。

### 8.2 慎重に扱うもの

- `class` の追加・削除
- CSS アニメーション対象の文字
- transform と `data-cetx` などの編集状態の同期
- リンク URL
- `display`、`position`、`z-index` など広い範囲へ影響するスタイル

特に位置・拡大縮小・回転は、見た目の CSS と編集ツールの `data-ce*` 状態が食い違わないようにする。

推奨：位置変更用の高水準操作を別途用意し、編集ツール自身の `applyTf()` と同じ規則で状態と CSS を同時更新する。

```json
{
  "op": "set_transform_state",
  "target": "ce_xxx",
  "translateX": 20,
  "translateY": -5,
  "scaleX": 1,
  "scaleY": 1,
  "rotate": 0
}
```

これは `set_style: transform` を自由入力させるより安全である。

### 8.3 将来対応する構造変更

構造変更は、任意 HTML ではなく、編集ツール側が所有する型付き命令として実装する。

例：

- `insert_component`
- `remove_component`
- `move_component`
- `duplicate_component`

挿入できる内容は、編集ツールに登録されたテンプレートに限定する。

構造変更を初期版へ含める必要はない。まずは位置・サイズ・文字・画像・装飾を安全に往復できる状態を完成させる。

## 9. 画像の扱い

Codex が画像を生成・差し替えする場合は、次の順序にする。

```text
1. 画像を所定のアップロード先へ保存
2. ファイル形式・サイズ・存在を検証
3. ブラウザから参照できる正規 URL を取得
4. replace_image パッチを作成
5. パッチ検証
6. 編集ツールで確認・保存
```

パッチに Windows の絶対パスを保存してはならない。

許可例：

```text
/uploads/work-pc-v2.png
```

禁止例：

```text
D:\images\work-pc-v2.png
```

## 10. セキュリティと入力検証

### 10.1 ファイル

- 対象は設定された `CAMP_DIR` 内だけに限定する
- 拡張子は `.html` または `.htm` の許可範囲に限定する
- `..`、絶対パス、URL エンコードを使ったパストラバーサルを拒否する
- パッチファイル名はユーザー入力をそのまま連結せず、検証済み対象名から決定する
- パッチと HTML は一時ファイル経由で原子的に保存する

### 10.2 属性と URL

- `on*` イベント属性を禁止する
- `javascript:` URL を禁止する
- `data:` URL は必要な画像 MIME のみに限定するか、原則禁止する
- `srcdoc` を禁止する
- `style` 属性全体の任意文字列置換は禁止し、プロパティ単位で処理する

### 10.3 制限

- 1 パッチあたりの最大操作数を設定する
- 1 操作の文字数を制限する
- パッチ全体のファイルサイズを制限する
- 許可 CSS プロパティを明示するか、危険な値を拒否する
- JSON Schema などで形式検証する

## 11. 既存処理への実装ポイント

現状コードでは、主に次の箇所が関係する。

### 11.1 `/camp/<path:filename>`

役割：キャンプ HTML を読み、編集バーを挿入して返している。

変更方針：

- HTML 読み込み後に対応パッチを取得する
- パッチ検証結果と revision をページへ渡す
- 編集バーの初期化前にパッチを適用する
- パッチなしの場合は現在と完全に同じ動作にする

### 11.2 `/api/save_camp_html`

役割：ブラウザから HTML 全文を受信し、finalize 後に原子的保存を行っている。

変更方針：

- `baseSha256` と `appliedPatchRevision` を受信する
- ファイル単位ロックを導入する
- 世代不一致を HTTP 409 にする
- HTML 保存成功後にだけパッチを消化済みにする
- レスポンスに新しい SHA-256 を含める

### 11.3 `cleanHtml()`

役割：現在の DOM を複製し、編集用 UI や一時効果を除去して保存用 HTML を作っている。

変更方針：

- パッチ適用用の一時スクリプト・管理 DOM を除去する
- パッチで変更された通常の style、文字、画像は維持する
- `data-ceid` を維持する
- 編集ツールの一時選択状態は従来どおり除去する

### 11.4 `applyTf(el)`

役割：`data-cetx` などから transform を組み立てている。

変更方針：

- Codex が transform 関連を変更する場合、この処理と同じ状態表現を使う
- CSS の transform だけを変えて内部状態と不一致にしない
- transform 用パッチ操作は専用バリデーターを通す

### 11.5 `cleanSection()`

役割：セクションを整理し、多くの編集用属性を削除している。

変更方針：

- 通常保存では `data-ceid` を維持する
- お気に入り素材化では `data-ceid` を削除する
- 素材挿入時に ID を再発行する
- 重複 ID の自動検査を追加する

## 12. 後方互換性

既存のキャンプ HTML を一度に全部変換しなくても動くようにする。

- `data-ceid` がない既存ページは、従来どおり閲覧・編集できる
- 編集モードで開いた際、必要に応じて ID を割り当てる
- 次回保存時に ID を正式 HTML へ保存する
- パッチが存在しない場合、既存の表示・保存結果を変えない
- 古いパッチ仕様を読み込む場合は、対応バージョンだけ移行し、不明なバージョンは拒否する

最初の移行では、「ID を付けただけで見た目が一切変わらない」ことを確認してからパッチ機能を有効にする。

## 13. エラー表示

ユーザーに内部 JSON を見せる必要はない。状態は分かりやすく表示する。

### 正常

```text
Codex の修正 8 件を適用しました。
このまま編集し、問題なければ「変更を保存」を押してください。
```

### 一部対象なし

```text
Codex の修正 8 件中、7 件を適用しました。
1 件は対象要素が削除されていたため適用していません。
```

### 競合

```text
Codex の修正後にページが別の場所で更新されています。
安全のため自動適用を中止しました。再読み込みして確認してください。
```

### 不正な操作

```text
安全に適用できない修正が含まれていたため、該当する変更を無効にしました。
```

## 14. テスト仕様

### 14.1 安定 ID

- ページを保存して再読込しても、同じ要素の ID が変わらない
- 要素を複製すると、元と複製先で ID が重複しない
- 子要素を含む複製でも、全 ID が新しくなる
- お気に入りセクションを二回挿入しても ID が重複しない
- 要素削除後、同じ ID が再利用されない

### 14.2 パッチ適用

- スタイル、文字、画像パッチが正しい対象だけに適用される
- 同じパッチを二回適用しても見た目が変わらない
- 対象 ID がない操作は警告され、ページ全体は表示できる
- 禁止属性、禁止 URL、任意スクリプトは拒否される
- 不明な `schemaVersion` は拒否される

### 14.3 保存

- パッチ適用後にツールで保存すると、変更結果が正式 HTML に残る
- 保存後に再読込しても、パッチが二重適用されない
- HTML 保存失敗時にパッチが消えない
- パッチ整理失敗時にも二重適用を防げる
- 古い `baseSha256` からの保存は HTTP 409 になり、HTML が上書きされない
- 古い patch revision からの保存は HTTP 409 になる

### 14.4 編集ツール回帰テスト

- 要素選択
- ドラッグ移動
- 矢印キー移動
- 拡大縮小
- 回転
- 文字編集
- undo / redo
- 画像差し替え
- アニメーション設定
- セクションのお気に入り保存と挿入
- ページ保存と再読込

上記が Codex パッチ適用前後で同じように動くこと。

### 14.5 必須の往復シナリオ

次の一連の操作を自動テストまたは手動受け入れテストにする。

```text
1. 既存ページを編集ツールで開く
2. 文字を移動して保存する
3. Codex CLI で余白・文字位置・画像の影を修正する
4. 同じページを編集ツールで開く
5. Codex の変更が見えることを確認する
6. その要素をツールでさらに移動する
7. 保存する
8. 再読込する
9. Codex とツール双方の変更が残っている
10. 未消化パッチが残っていない
11. 通常の編集操作が壊れていない
```

このシナリオを満たさない限り、「Codex とツールで共同編集可能」とはみなさない。

## 15. 実装順序

### Phase 1: 安定 ID

- `data-ceid` の発行
- 通常保存での維持
- 複製時の再発行
- お気に入り挿入時の再発行
- 重複検査
- 見た目と既存編集機能の回帰テスト

- JSON Schema
- パッチリポジトリ層
- SHA-256 と revision
- 許可操作のバリデーター
- 原子的保存

### Phase 3: 読み込み時の適用

- 編集機能初期化前に適用する
- 適用レポートとユーザー通知

### Phase 4: 保存時の正式取り込み

- 必要性を確認した後にのみ実装する

- 任意 HTML 操作は導入しない

## 16. 完了条件

次をすべて満たしたとき、本機能を完成とする。

- ユーザーが編集ツールで保存したページを、Codex が専用パッチで修正できる
- Codex の修正後、ユーザーが編集ツールで同じ要素を選択・移動・保存できる
- 保存と再読込後も双方の変更が維持される
- 同じパッチが二重適用されない
- 競合時に変更を失わず、保存を安全に中止できる
- 複製やお気に入り挿入で安定 ID が重複しない
- Codex が禁止操作を行えない
- パッチがない既存ページの挙動が変わらない
- 必須の往復シナリオと既存編集機能の回帰テストが通る

## 17. Claude Code への実装指示

Claude Code は、この仕様に基づき次の方針で実装すること。

1. まず既存コードの保存・読み込み・複製・お気に入り処理を再確認する
2. 既存の `data-ce*` の意味と削除タイミングを調査する
3. Phase 1 から順番に、小さく実装して各段階でテストする
4. 既存 HTML の見た目を変えない
5. 既存の全 HTML を一括書き換えしない
6. パッチなしの処理経路を変えない
7. ファイル保存は既存の原子的保存方式を維持する
8. 競合時は強制上書きせず HTTP 409 にする
9. Codex に HTML 直接編集をさせる仕組みは作らない
10. 実装後、必須の往復シナリオを実際のキャンプ HTML で確認する

実装前に、変更予定ファイル、追加予定ファイル、既存挙動への影響、テスト計画を提示すること。

実装中に仕様と現在のコードが食い違う場合、現在のコードを正として差異を報告し、安全性を落とす独自判断は行わないこと。

## 18. 補足：`codex_test/layout-fix.js` について

`codex_test/layout-fix.js` は、HTML 本体を直接変更せずに見た目を上書きできることを確認するための試作である。

本番の共同編集機能として、そのまま各ページへ JavaScript を追加していく方式は採用しない。

試作から本番へ引き継ぐ考え方は「変更を別ファイルにする」点だけであり、本番では次を追加する。

- 安定 ID
- 検証済みパッチ形式
- 世代管理
- 競合検知
- 編集開始前の適用
- ツール保存時の正式取り込み
- 適用済みパッチの二重適用防止

これらが揃って初めて、ツール → Codex → ツールの往復運用を安全に行える。
