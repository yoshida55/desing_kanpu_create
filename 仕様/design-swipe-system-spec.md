# デザイン参照ストック & 曖昧検索システム 仕様書

最終更新: 2026-06-30

---

## 1. 目的・背景

これまでの業務は「デザインカンプを元にホームページをHTML/CSS実装する」のが主だった。
今後はデザイン工程から関わる可能性が出てきたため、**自分が良いと感じたWebサイトの「見た目・雰囲気」を集約・検索・再利用できる土台**を作る。

最終的なゴールは、集めたデザイン資産を使って **デザインカンプの叩き台を素早く作り出せる** ようにすること。

---

## 2. 最終的に作りたいもの（ビジョン）

本質的には、これは **「デザイン版のRAG（検索して生成に渡す知識ベース）」** である。
全体は4つの層で構成される：

1. **集める** — 良いと思ったサイトをスクショ＋メタデータで蓄積する
2. **探す** — 見た目・雰囲気で曖昧検索する（言葉でも、画像でも）
3. **参照する** — URLで実物へ飛び、動き・アニメを確認する
4. **生成する** — 検索で引いたセクション＋デザイントークンをAIに渡し、新しいカンプのHTML下書きを生成→反復する

ポイントは、**「1サイトを丸ごと複製する」のではなく「自分のストックから新しいものを生成する」** こと。
これが複製と参照の線引きであり、システムの設計思想の核。

---

## 3. システム全体像（パイプライン）

```
URL ─▶ [取り込み] ─▶ スクショ＋メタデータ ─▶ [埋め込み] ─▶ ベクトル
                                                              │
                                       ┌──────────────────────┘
                                       ▼
                              [検索] ─▶ カード（スクショ＋URLリンク）
                                       │
                                       ▼
                              [カンプ生成]（最終目標）

  ※ アニメーション取得は本線とは別パス（オンデマンド）
```

検索の主軸は **「見た目のパターン・雰囲気」** での曖昧検索。機能名での検索（例：「スタッガー演出」）は後付けのタグ層の役割とし、初期段階では扱わない。

## 4. 機能仕様

### 4.1 取り込み（ingest）

- **入力**：サイトのURL。
  - 1件ずつCLIで渡す / URLリスト（1行1URL）を一括で渡す
  - 将来：ブラウザ拡張・ブックマークレットで「今見ているページを保存」も乗せられる（パイプラインを呼ぶだけなので後付け可能）
- **撮影ツール**：Playwright（Chromium / headless）。
- **1回のページロードから2枚撮る**：
  - `firstview`（viewport）= **検索用**（雰囲気が最も濃縮されている）
  - `fullpage`（全体）= 見返す用・後でセクション分割する素材
- **撮影条件は固定する**（似た画像検索の精度がブレないように）：
  - viewport 1440×900 / deviceScaleFactor 2 / User-Agent固定
- **前処理**：
  - cookie同意バナーを best-effort で閉じる（覆われたまま撮ると検索が濁るため）
  - 最下部までスクロールして lazy-load を発火させてから先頭に戻す
- **重複排除**：URLで判定。`--force` で撮り直し。
- **撮影日時を記録**：サイトはリニューアルするので、後で撮り直し判断ができるように。

**既知の弱点（割り切る）**
- 同意バナーの自動クローズは完璧ではない（文言が合わなければ手動で追加）
- headlessをブロックするサイトがある（その場合は非headlessや別手段）
- `position: fixed` のヘッダーは fullpage 撮影で重複して写りうる

---

### 4.2 データスキーマ（SQLite: `site` テーブル）

```
site
├─ id                   TEXT  PRIMARY KEY     -- URLのハッシュ等
├─ url                  TEXT  UNIQUE NOT NULL -- 本物へ飛ぶリンクの本命
├─ captured_at          TEXT  NOT NULL        -- 撮影日時(ISO)
├─ firstview_path       TEXT  NOT NULL        -- 検索用(viewport)
├─ fullpage_path        TEXT  NOT NULL        -- 見返す/分割用
├─ viewport_w           INTEGER NOT NULL
├─ viewport_h           INTEGER NOT NULL
├─ device_scale_factor  INTEGER NOT NULL
├─ vibe_description      TEXT                 -- 後でVision LLMが生成（雰囲気の描写文）
├─ auto_tags             TEXT                 -- 自動タグ（語彙は事前に固定する）
├─ manual_tags           TEXT
├─ image_embedding       BLOB                 -- SigLIP-2の画像ベクトル(float32)
├─ embed_dim             INTEGER              -- 埋め込み次元(実測値を記録)
├─ embed_model_name      TEXT                 -- 差し替え検知用
├─ embed_version         TEXT                 -- 再埋め込み判定用
├─ animation_status      TEXT NOT NULL DEFAULT 'none'  -- none / video / extracted
├─ animation_video_path  TEXT                 -- スクロール録画(nullable)
├─ animation_snippets    TEXT                 -- CSS/Lottie抽出(nullable)
└─ animation_libs        TEXT                 -- 検出したライブラリ名(nullable)
```

設計上の要点：
- **元画像（firstview / fullpage）は必ず保存する** → モデルを変えても何度でも再埋め込みできる
- **`embed_model_name` / `embed_version` / `embed_dim` を持つ** → 将来モデルを差し替えたとき「どのレコードが古いか」を判定して再埋め込みできる
- **アニメ系カラムは optional** → アニメは後から、欲しいサイトにだけ足す

---

### 4.3 埋め込み（embed）

- **モデル**：SigLIP-2 / `google/siglip2-so400m-patch14-384`（出力 **1152次元**、多言語=日本語OK、Apache 2.0、CPU/GPU両対応）
  - 2026時点で画像↔テキスト類似の最強クラスの公開モデル
  - **モデルは抽象化して持つ**：モデルIDは設定値、次元数はハードコードせず埋め込み時に実測した値を記録する
  - VRAM：RTX 3070Ti（8GB）で余裕。重ければ `siglip2-base-patch16-384` 等に変更（設定値の差し替えだけ）
- **処理**：`firstview.png` を画像エンコーダに通す → **L2正規化** → DBに `image_embedding`(BLOB) として保存
- **記録**：`embed_model_name` / `embed_version` / `embed_dim`
- **対象**：まだ埋め込みが無い、またはモデルが変わったレコードだけ（`--force` で全件再処理）

---

### 4.4 検索（search）

**2系統を持つ：**

- **text → image（本命）**：クエリの言葉をテキストエンコーダでベクトル化 → 全画像ベクトルと比較 → 上位N
  - 「雰囲気を言葉で探す」。日本語クエリがそのまま使える。
- **image → image**：参照画像を画像エンコーダでベクトル化 → 比較 → 上位N
  - 「これに似たやつ」を芋づる式に。

**類似度**：保存時にL2正規化済みなので、**正規化ベクトル同士の内積（= cosine）** で計算する。
- SigLIP系は sigmoid 損失でスコアの絶対値の感覚がCLIPと違うため、**「何点以上を表示」のような閾値は決め打ちせず、実データを見て調整する** 前提。

**保存・計算方式**：個人規模（数百〜数千件）では専用ベクトルDBは過剰。
- 埋め込みをDBに持ち、検索時に全件メモリに載せて **numpyで総当たり** で十分速い。
- 件数が万単位になったら sqlite-vec 等に差し替える（保存と検索を分離してあるので差し替え可能）。

### 4.5 結果表示

**Phase 1：静的HTML**
- CLIで検索 → `results.html` を出力 → ブラウザで開く
- カード1枚＝**スクショ（firstview）＋ スコア ＋ URLリンク ＋ 撮影日**
- URLリンクを押せばライブサイトへ飛び、**動き・アニメを実物で確認できる**
- まずこれで「SigLIP-2の検索が使い物になるか」を安く検証する

**Phase 2：ローカルビューア（小さなサーバー）**
- ブラウザに検索ボックスを置き、モデルを常駐させる
- 理由：雰囲気検索は言葉を変えて何度も試す作業（「青っぽい」→「もっと暗い青」→「上品な青系」）。
  CLI都度起動だと毎回モデル読み込みの数秒を待つことになり、試行のテンポが死ぬ。ビューアなら2回目以降が一瞬。

**切替トリガー**：静的HTMLで「打ち直し→待ち」が面倒に感じたら、ビューアに上げる。

---

### 4.6 アニメーション取得（Feature 4）

**原則：静止画にアニメは入らない。** アニメは本線とは別パスで、**撮りたいサイトだけ・オンデマンド**で取る（全サイト自動にはしない＝動画は重く、大半のサイトでは不要）。

**再現度は3段階に分かれる：**

| 種類 | 取得方法 | 性質 |
|------|----------|------|
| CSS / Lottie | DevTools・拡張でコード抽出、LottieはJSON | **再利用できるコード** |
| JS駆動（GSAP・スクロール系） | 抽出不可。スクロール録画(動画/GIF)＋ライブラリ名を保存 | 参照のみ |
| WebGL / Canvas | 参照リンクのみ | 参照のみ |

**本命はURL**：飛べば動きもHTMLも本物で確認できる。"抽出が難しい"問題を丸ごと回避する一番きれいな手段。
- 注意：サイトは消える・作り変わる（リンク切れ）。対策として **スクショ（と、欲しいサイトは動画）を保険として残す**。

**重要な発想**：自分の目的（カンプ作り）では、アニメの **完全抽出は不要**。必要なのは「どんな演出か思い出せる参照」と「似たものを作れること」。後者は今のAIに **言葉で指示すればGSAP/CSSを書かせられる**。つまり「抽出が難しい」は「AIで再現する」ことで回避する。

---

### 4.7 カンプ生成（最終目標）

**方針**：1サイトのクローンではなく、**自分のストックから新しいカンプを生成する（デザインRAG）**。

**フロー**：
1. 検索で「雰囲気・セクション」を自分のストックから引く
2. デザイントークン（色・フォント・余白）を抽出して添える
3. それらを文脈としてAIに渡し、**新しい**カンプのHTML下書きを生成
4. アニメは「こういう演出」と言葉で足して再現させる
5. Claude Design / ブラウザで反復して仕上げる

**形式**：**スクショ→HTML** を採用。
- 現状のAIは静的レイアウト・色・タイポの再現は実用段階。
- **SVGは静的モック止まりで実装に進めない**ため、カンプ形式としては非推奨。

**注意**：
- 「ピクセルパーフェクト/99%」はベンダーの宣伝。実際はアニメ・独自イラスト・チャートは近似で **手直し前提**。
- 複製にならないよう「参照 → 作り直し」を徹底する。

## 5. 実装フェーズ（ロードマップ）

- **Phase 1（現在地）**：取り込み + 埋め込み + 静的HTML検索 → **SigLIP-2がちゃんと効くか検証する**
- **Phase 2**：ローカルビューア化（反復検索を快適に）
- **Phase 3**：自動タグ付け／雰囲気描写文の埋め込み（ハイブリッド）、デザイントークン抽出、アニメのオンデマンド取得
- **Phase 4**：カンプ生成（RAG）

---

## 6. 検証方法（Phase 1のゴール判定）

プロトタイプで一番大事なのは見た目ではなく **「効いているかを測れること」**。

- 検証前に **「このクエリを打ったら、このサイトが上位に来てほしい」を5〜10個メモ** しておく
- 3つの観点を **別々に** 確認する：
  1. **色・トーンの雰囲気**（SigLIPの得意領域）が当たるか ← まずここ
  2. **抽象的な雰囲気**（高級感・上品さ）はどうか ← 弱ければ「雰囲気描写文の埋め込み」ハイブリッドの出番
  3. **image → image（似た画像）** の納得感はあるか
- 「なんとなく良さそう」ではなく **差分で判定** できる状態を作る（モデルやクエリの書き方を変えたとき、良くなったか分かる）

## 7. 技術選定と理由（まとめ）

| 項目 | 採用 | 理由 |
|------|------|------|
| 埋め込みモデル | SigLIP-2 SO400M | 2026時点で画像↔テキスト類似の最強クラス・多言語・Apache・ローカル可 |
| 撮影 | Playwright | コード駆動で確実。viewport / fullpage / 動画すべて対応 |
| 検索用に撮る画像 | viewport（ファーストビュー） | 埋め込みモデルは正方形寄りに縮小するため、縦長のfullpageは雰囲気が潰れる。雰囲気はファーストビューに濃縮されている |
| ベクトル保存・検索 | DB + numpy総当たり | 個人規模に専用ベクトルDBは過剰。万単位になったらsqlite-vec等へ |
| 結果表示 | 静的HTML → ビューア | 検証を安く先に。反復が要ると分かってからビューア化 |
| カンプ形式 | スクショ→HTML | SVGは実装に進めない袋小路 |
| アニメ | 別パス・オンデマンド | 動画は重く大半は不要。URL＋動画＋スクショで参照運用 |

## 9. 既知の制約・注意点（正直なところ）

- **同意バナーの自動クローズは不完全** — 漏れたら文言を手動追加。
- **headlessをブロックするサイトがある** — 個別対応。
- **抽象的な雰囲気はSigLIP単体だと弱い** — 「雰囲気描写文も埋め込む」ハイブリッドで補える（Phase 3）。
- **JS駆動アニメは抽出できない** — 動画＋ライブラリ名の参照運用で割り切る。
- **著作権・スクレイピング** — 個人のリファレンスとしての収集は問題ないが、納品に流すときは「参照→作り直し」を徹底。robots.txt・利用規約・レート制限を尊重する。（法的な最終判断は専門家に確認する。）
- **リンク切れ** — URLは消える前提。スクショ（と動画）を保険として残す設計にしてある。
